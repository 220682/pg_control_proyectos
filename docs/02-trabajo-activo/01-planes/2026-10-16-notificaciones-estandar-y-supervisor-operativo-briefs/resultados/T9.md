## Mecanismos de Supabase que se usaron

- **Verificar la contraseña actual:** cliente aparte de `@supabase/supabase-js` con `persistSession: false`, `autoRefreshToken: false` y `signInWithPassword` con el correo de la sesión; después `signOut({ scope: 'local' })` del mismo cliente aislado. No lee ni escribe cookies, así que la sesión del navegador no cambia. Validado solo con doble.
- **Cambiar la contraseña:** `admin.auth.admin.updateUserById(<id de la sesión>, { password })`, la misma llamada con la que el administrador fija la contraseña al crear el usuario. Se eligió esta y no `updateUser({ password })` porque este último puede exigir reautenticación según la configuración «secure password change» del proyecto, que no se puede comprobar sin tocar una cuenta real. Ningún error de Supabase se devuelve tal cual.
- **Cambiar el correo:** `supabase.auth.updateUser({ email }, { emailRedirectTo: <URL pública>/mi-entorno })` con la sesión del servidor. No se usa la llamada de administrador, que cambiaría el correo sin confirmación. Un correo repetido (`email_exists`) responde 409.
- **Guardar el celular:** la tabla `perfiles` no tiene política de escritura para usuarios (`db/003_rls.sql`), por eso la ruta escribe con el cliente de administrador, siempre sobre el id de la sesión y después de validar el permiso en código.
